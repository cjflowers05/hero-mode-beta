## 1. Quick Start

### Running locally
There is no build step. The entire app is `index.html`.

Serve from the project root with any static file server, e.g.:
- **VS Code Live Server** — right-click `index.html` → Open with Live Server (default port 5500)
- **Python:** `python -m http.server 8080`
- **npm:** `npx serve .`

Open `http://localhost:<port>/` in a browser. The app registers a service worker on first load.

### After editing index.html
Always reload the page **after saving** before testing. If edits don't appear, the service worker may be serving a cached version — see [Section 9 — Dev Gotchas](#9-key-dev-gotchas).

### For native (iOS / Android)
```bash
npm run sync-www    # copies index.html + assets → www/
npm run cap:sync    # syncs www/ → android/ and ios/ projects
npm run cap:android # opens Android Studio (install app from there)
# npm run cap:ios   # needs a Mac + Xcode
```

## 2. Architecture Overview

Hero Mode is a **single-file PWA** — the entire application lives in one `index.html` file (~22,000+ lines). There is no framework, no bundler, no build step. Plain HTML, CSS, and vanilla JavaScript.

**Why single-file:** keeps the app portable, easy to back up, and wrappable with Capacitor for native deployment without a complex build pipeline.

**Storage:** everything is stored in `localStorage` on the device. No backend, no server, no accounts (as of v1). Data never leaves the device unless the user manually exports a backup.

**Service worker (`sw.js`):** makes the app work offline. Uses network-first strategy — tries to fetch fresh content, falls back to cache. Cache version must be bumped on every meaningful deploy (see [Section 6.14](#614-service-worker--caching)).

## 4. How index.html Is Organized

The file has three major sections: **CSS**, **HTML**, and **JavaScript** (split into multiple `<script>` blocks).

### CSS (top of file)
All styles are inline in a `<style>` block at the top. Key CSS variables are defined on `:root` and overridden per theme. There is no external stylesheet.

Notable CSS sections (search for these comments):
- `/* ── VARIABLES / RESET ── */` — CSS custom properties (color tokens, fonts)
- `/* ── TABS ── */` — bottom tab bar
- `/* ── WORKOUT / TRAINING ── */` — exercise rows, plan cards
- `/* ── GAMIFICATION ── */` — XP bar, badges, trophy case, FX overlays
- `/* ── DECK OF CARDS WORKOUT ── */` — card game UI
- `/* ── SESSION SUMMARY ── */` — post-session overlay
- `/* ── CUSTOM WORKOUT BUILDER ── */` — custom session UI

### HTML (middle of file)
The main content is five tabs plus a collection of modals/overlays:

```
<body>
  #hero-splash          ← Launch splash screen (auto-hides at 1.8s)
  #tab-today            ← Today tab (home dashboard)
  #tab-workout          ← Train tab (workout plan + logging)
  #tab-nutrition        ← Nutrition tab
  #tab-roadmap          ← Progress/Roadmap tab (charts, history)
  #tab-wellness         ← Wellness tab (sleep, water, measurements)
  <!-- dozens of modal overlays: #goals-overlay, #dc-overlay, etc. -->
  <nav>                 ← Bottom tab bar
</body>
```

### JavaScript (bottom of file)
Three `<script>` blocks in order:

**Block 1 — Plan Generator & Storage Migration**
- Runs immediately on page load
- Handles `heromode_*` → storage key migration from old versions
- Contains `hmGeneratePlan()`, `hmRenderTrain()`, all plan-building logic
- Contains the `EX` exercise database object and `HM_*` plan constants

**Block 2 — Main App Logic**
- The bulk of the app (~15,000 lines)
- All feature functions live here: logging, nutrition, cardio, charts, quests, etc.

**Block 3 — Hero Identity Engine**
- Last script block
- XP system, awards, profiles, themes, sounds, FX overlays
- Also contains `HeroNative` bridge for Capacitor
- `window.hmXP`, `window.hmSfx`, `window.hmHeroFX`, `window.hmBadgePop` all exposed here

**Finding things:** use your editor's Find in File (`Ctrl+F` or `Cmd+F`) to search for function names or HTML IDs. Everything is in one file so search is the primary navigation tool.

## 5. Data Layer — localStorage Reference

All data is stored in `localStorage`. Keys are prefixed `heromode-` or `hero-` (legacy keys from `thormode-`/`thor-` were auto-migrated on first load).

| Key | Type | Contents |
|---|---|---|
| `heromode_goals_v1` | JSON object | User's goal selections from the onboarding form (goal, days/week, equipment, experience, etc.) |
| `heromode-log` | JSON object | All workout logs: `{ "YYYY-MM-DD": { "exerciseKey": [{w, r}, ...] } }` |
| `heromode-prs` | JSON object | Personal records per exercise: `{ "exerciseKey": {w, r, e1rm, date} }` |
| `heromode-completed` | JSON array | List of completed day slots (date + slot strings) |
| `hero-profiles` | JSON object | All user profiles: `{ active: "p1", profiles: { p1: {name, emoji, photo, theme, ...} } }` |
| `hero-xp--{profileId}` | JSON object | XP state per profile: `{ xp, freezes, counters:{...}, badges:{}, login:{}, story:{} }` |
| `heroTheme` | string | Currently active theme ID (e.g. `"warrior"`, `"phoenix"`) |
| `hero-plan-edits--{profileId}` | JSON object | User's exercise swaps/set overrides: `{ "phaseId|dayIdx|exKey": {action, ...} }` |
| `hero-feedback--{profileId}` | JSON object | Exercise/workout feedback (fav/hard marks + notes) |
| `hero-weekly--{profileId}` | JSON array | Weekly review history (last 52 entries) |
| `hero-trim--{profileId}` | JSON object | Today's time-crunch trim state (resets daily) |
| `hero-cardio-last` | JSON object | Last cardio session (for repeat-last feature) |
| `hm-session-note-{YYYY-MM-DD}` | string | User's written note from the post-session summary |
| `hero-tour-done` | string | `"1"` if first-run tour completed |
| `hero-tour-date` | string | Date of last tour (quarterly refresh gate) |
| `hero-last-backup` | string | ISO date of last backup export |
| `hero-install-dismissed` | string | `"1"` if install PWA prompt dismissed |
| `hm-train-layout` | JSON object | Train tab section visibility prefs |
| `hm-pet-name` | string | User's pet mascot name |
| `td-*` | various | Today tab layout customization prefs |

**Reading log data in code:**
```js
const log = slLoad();           // { "YYYY-MM-DD": { exKey: [{w,r},...] } }
const prs = slLoadPRs();        // { exKey: {w, r, e1rm, date} }
const xp  = hmXPLoad();         // full XP state object
```

### 6.1 Plan Builder & Goal System

**What it does:** Takes the user's goals from the onboarding form and generates a phased workout plan.

**Where to find it:**
- Onboarding overlay HTML: search `id="goals-overlay"`
- Plan generation: `function hmGeneratePlan()` (Block 1)
- Plan rendering to DOM: `function hmRenderTrain()`
- Exercise database: `const EX = { ... }` (Block 1) — every exercise key, name, equipment, tags
- Phase/split constants: `HM_SPLITS`, `HM_DAY_T`, `HM_PHASE_META`, `HM_SCHEMES`

**How it works:**
1. User fills out `#goals-overlay` (goal type, days/week, equipment, experience level, body weight)
2. On submit, goals saved to `localStorage['heromode_goals_v1']`
3. `hmGeneratePlan(goals)` builds a plan array of phases → days → exercises
4. `hmRenderTrain()` converts that plan to HTML and inserts it into `#tab-workout`
5. `hmRefreshIntegrations()` re-runs all row-level logic after rendering (done buttons, swap buttons, log buttons, etc.)

**Phase progression (earn-to-advance):**
Phases no longer auto-advance on a calendar schedule. Each phase has unlock criteria tracked in `localStorage['hero-phase-state--{pid}']`:
- Foundation → Build: 6 completed sessions since entering Foundation
- Build → Peak: 8 sessions + any PR logged since entering Build
- Bypass (same fanfare): available after 2 weeks in the phase regardless of criteria

Key functions: `hmPhaseStateLoad()`, `hmPhaseStateSave(s)`, `hmPhaseProgress()`, `hmPhaseAdvance()`. Sessions are counted via `hmPhaseSessionCount(startDate)` reading `heromode_v2.completedDays` directly. PRs are checked via `hmPhasePRAfter(startDate)` reading `hero-prs` directly (not via Block 2 helpers — these functions run from Block 1).

**To add a new goal type:**
- Add a goal ID to the `#gp-goal` button group in the HTML
- Add a split definition to `HM_SPLITS`
- Add phase metadata to `HM_PHASE_META`
- Add day templates to `HM_DAY_T`

**To add a new exercise:**
- Add an entry to the `EX` object: `{ name, equip, tags, type, video }` — `video` is the filename (without extension) in `MoveKit_Videos/` (e.g. `"BenchPress"`)
- Add it to the relevant `HM_*` slot arrays if you want the plan generator to pick it automatically
- To classify it for smart nudges / XP calculation, check `SL_COMPOUND`, `SL_TIMED`, `SL_BODYWEIGHT`

### 6.2 Exercise Logging & PRs

**What it does:** Handles the set-by-set logging sheet, PR detection, weight nudges, and saves everything to localStorage.

**Where to find it:**
- Open log sheet: `function openLogSheet(key)` — opens the bottom sheet for an exercise
- Save a set: `function slLogSet(key, w, r)` — the core logging function, also fires XP + PR check
- Load all logs: `function slLoad()` — returns the entire log object
- Load PRs: `function slLoadPRs()` — returns PR object
- Smart overload nudge: `function slSmartNudge(key)` — analyzes recent sessions, returns `{type, newWeight, ...}` or null
- Refresh an exercise row: `function slRefreshRow(key)` — updates the row UI (done state, overload tag)
- Exercise type: `function slExType(key)` — returns `'weighted'`, `'bodyweight'`, `'timed'`, etc.

**How sets are stored:**
```js
// localStorage['heromode-log']
{
  "2026-08-06": {
    "benchpress": [ {w: 135, r: 8}, {w: 135, r: 8}, {w: 145, r: 6} ],
    "squat":      [ {w: 185, r: 5} ]
  }
}
```

**PR detection:** happens inside `slLogSet()`. If the new e1RM (estimated 1-rep max using Epley formula) beats the stored PR, `hmXP('prs', 40)` is called and a badge/FX fires.

**Weight nudges (overload tags):** `slSmartNudge(key)` compares last 2 sessions and recommends: `increase` (add weight), `reps` (add a rep), `maintain` (consolidate), or `start` (first session suggestion). The `.ex-overload-tag` element on each plan row shows this before the user taps LOG.

**Units:** all weights stored in **lbs** always. Display converts via `hmDispW()` if user set kg in their goals. Never change the storage unit — it would break all historical data.

### 6.3 XP, Levels & Awards

**What it does:** Tracks experience points, calculates level/rank, manages 40+ awards (badges + trophies), fires badge/trophy reveal animations.

**Where to find it:** Block 3 (identity engine), search:
- `function hmXPLoad()` — reads XP state for active profile
- `function hmXPSave(s)` — saves XP state
- `function hmXP(category, amount)` — the main XP function; call this to award XP
- `function hmLevelInfo(xp)` — returns `{lvl, rem, need}` for a given XP total
- `function hmRankFor(lvl)` — returns rank name (ROOKIE → IMMORTAL)
- `const HM_AWARDS` — the array of all badge/trophy definitions
- Award dispatch: search `newAwards.forEach` — this is where badge/trophy FX fires

**XP hooks (where XP is awarded):**
| Event | Call | Amount |
|---|---|---|
| Log a set | `hmXP('sets', amount)` | 5–8 XP (varies by exercise type) |
| Log a PR | inside `slLogSet` | +40 XP |
| Mark day done | `toggleDayDone()` | +50 XP |
| Perfect week bonus | inside week check | +100 XP |
| Cardio session | `cardioCommitSession()` | +15 XP |
| Daily login | `hmLoginTick()` | +10 XP |
| Water first glass | `waterAdd()` | +5 XP |
| Check-in | check-in save | +10 XP |
| Quest claimed | `hmClaimQuest()` | +25 XP |
| Chest opened | `hmOpenChest()` | +50 XP |
| Deck of Cards complete | `_dcSummaryHtml()` | +30 XP |

**Adding a new badge:**
1. Add to `HM_AWARDS` array with `{id, name, ico, col, cond(s), trophy?}`
2. The `cond` function receives the XP state object `s` and returns true/false
3. Trophies (gold tier) use `trophy: true` — they fire `hmHeroFX()` instead of `hmBadgePop()`
4. Awards are checked inside `hmXP()` via `hmCheckAwards(s)` — runs on every XP call

**Level thresholds:** `300 + (level - 1) × 150` XP per level (so level 1→2 = 300 XP, level 2→3 = 450 XP, etc.)

**Rank system:** levels 1–3 = ROOKIE, 4–6 = FIGHTER, 7–9 = WARRIOR, 10–12 = CHAMPION, etc. Nine ranks total up to IMMORTAL.

### 6.5 Themes & Sound

**What it does:** 15 visual themes that change colors, header pattern, emblem, and sound tone. Three themes are level-gated.

**Where to find it:** Block 3, search:
- `const HERO_THEMES` — array of all 15 theme definitions
- `function hmThemeUnlocked(t)` — returns true if user's level meets the theme requirement
- `function showThemePicker()` — opens the theme picker overlay
- `function hmApplyTheme(id)` — applies a theme (sets CSS variables + saves)
- `function hmSfx(name)` — plays a sound effect (done / badge / trophy / level / pr / tap)
- `function hmAudioUnlock()` — must be called on first user gesture (iOS audio restriction)

**Theme definition shape:**
```js
{
  id: "warrior",
  name: "Warrior",
  accent: "#C9A84C",          // gold color
  accentRgb: "201,168,76",    // for rgba() usage
  bg: "#0A0C10",
  bg2: "#12151C",
  // ...more color tokens...
  emblem: "⚔️",               // or path to image
  patImg: "...",              // CSS background-image for header pattern
  tone: 440,                  // base frequency for WebAudio SFX
  lockLevel: null             // null = always available; 8/15/20 = locked
}
```

**Adding a new theme:**
1. Add to `HERO_THEMES` array with all required color tokens
2. Keep `--text3` around L≈40% HSL for legibility (learned from bug history)
3. If level-gated, set `lockLevel` and it auto-locks/unlocks via `hmThemeUnlocked()`

**Sound effects** are generated with WebAudio API — no audio files needed. `hmSfx('done')` plays a completion tone, `'trophy'` plays a fanfare, etc.

### 6.6 Daily Quests & Chest

**What it does:** Three daily quests refresh each day. Completing all three unlocks a chest reward (+50 XP + FX). Quests are deterministic (same for everyone on a given day) so no backend is needed.

**Where to find it:**
- Quest HTML: search `id="daily-quests"` in the HTML
- Quest state: `function hmQuestState(xpState)` — returns `{slots:[...], claimed:{}, chest:bool}`
- Render quests: `function hmRenderQuests()`
- Claim a quest: `function hmClaimQuest(idx)`
- Open chest: `function hmOpenChest()` — Phase 1 (video plays)
- Chest reveal: `function hmChestReveal()` — Phase 2 (reward screen, after video ends)
- Quest pools: `const HM_QUEST_POOLS` — train/fuel/body categories

**Quest selection:** `hmQuestState()` uses `dayOfYear × seed` to pick deterministically from pools. Same day = same 3 quests for all users. Quests reset at midnight (keyed by `YYYY-MM-DD`).

**Chest video:** `assets/ui/chest_reveal.mp4` plays fullscreen when the chest is opened. The video `ended` event triggers `hmChestReveal()`. "CLAIM REWARD ▸" button appears after 1.2s as a skip option.

### 6.7 Session Summary & History

**What it does:** After marking a workout done, a post-session summary overlay appears showing stats. Users can add a note. Past sessions are shown in Session History on the Training tab.

**Custom workout completion:** `cwFinishWorkout()` is the custom-session equivalent of `toggleDayDone()`. It calls `addCompletedSlot(today, 'custom-workout')` + `saveDB()` + `hmXP('days', 50)` + `showSessionSummary()`. This makes custom sessions fully count toward streaks, scorecard "Workout Done", and training history — same as plan sessions. The FINISH WORKOUT button appears in `cwRenderTodayAddon` once ≥1 exercise or cardio is marked done; it swaps to a "✓ WORKOUT LOGGED" badge after completion.

**Where to find it:**
- Show summary: `function showSessionSummary()` — called 350ms after `toggleDayDone()` or `cwFinishWorkout()`
- Close summary: `window.closeSessionSummary()`
- Session notes: saved to `localStorage['hm-session-note-{YYYY-MM-DD}']` via the textarea's `oninput`
- Session history: `function renderSessionHistory()` — renders into `#chart-session-history`
- Toggle row: `window.shToggle(i)` — expand/collapse a history row

**Summary overlay ID:** `#sess-sum-overlay` (created dynamically, not in static HTML)

**Note storage key format:** `hm-session-note-2026-08-06` (ISO date)

### 6.9 Deck of Cards Workout

**What it does:** A full-screen military-style workout — flip a card, the number = reps, the suit = exercise. Works through a full 52-card deck.

**Where to find it:**
- Open/close: `function openDeckWorkout()`, `function closeDeckWorkout()`
- Overlay HTML: `id="dc-overlay"` in the static HTML; body content generated dynamically
- Render: `function _dcRender()` — rebuilds `#dc-body` innerHTML based on game phase
- Setup screen: `function _dcSetupHtml()` — shows suit→exercise mapping with Ace card images
- Game screen: `function _dcGameHtml()` — shows current card + reps + controls
- Card image path: `function _dcCardImgSrc(val, suit)` — maps value + suit → filename in `assets/ui/deck_cards/`
- Image error fallback: `window._dcImgError(img)` — injects a text card when image file is missing
- Card done: `function dcCardDone()` — advances to next card
- Skip: `function dcSkip()`
- Summary: `function _dcSummaryHtml()` — shown when deck is complete

**Card image naming convention:**
- Numbers 2–10: `{number}_{suit}.png` (e.g. `7_hearts.png`)
- Face cards: `{Name}_{suit}.png` (e.g. `Jack_clubs.png`) — BUT some filenames are lowercase:
  - `jack_diamonds.png`, `king_diamonds.png`, `king_spades.png`, `queen_spades.png`
  - `_dcCardImgSrc()` handles all these cases automatically
- Ace: `Ace_{suit}.png` (all four suits, all capital A)
- Joker: `Joker.png` (not currently used in gameplay)

**Game state:** stored in `let _dc = null` — reset when workout closes. Shape:
```js
_dc = {
  phase: 'setup' | 'game' | 'done',
  deck: [{suit, val}, ...],   // shuffled 52 cards
  idx: 0,                      // current card index
  mapping: { spades:{key,label}, hearts:{...}, diamonds:{...}, clubs:{...} },
  repsBySuit: { spades:0, hearts:0, diamonds:0, clubs:0 },
  totalReps: 0,
  startTime: Date.now()
}
```

**Suit defaults:** ♠ Push-Ups, ♥ Sit-Ups, ♦ Air Squats, ♣ Burpees. Users can tap any suit card to pick a different bodyweight exercise.

**Exercise picker (`dcPickEx`):** Filters exercises for the suit picker using `SL_BODYWEIGHT.has(k) || (e.tag && e.tag.includes('Bodyweight'))`. Do NOT filter on `e.equip` or `e.tags` — EX entries use `e.tag` (a string like `"Full Body · Bodyweight"`), not an `equip` property or a `tags` array.

### 6.10 Gamification FX

**What it does:** Three video-powered reveal moments for badges, trophies, and chest rewards.

**Badge reveal (regular badges):**
- Function: `function hmBadgePop(b)` — `b = {ico, name, col}`
- Plays `assets/ui/anvil_reveal.mp4` fullscreen for ~1.8s (only one overlay at a time)
- Badge toast slides in from bottom at 700ms (z-index 11000, above the video overlay)
- Badge toast auto-removes after 3.2s from appearance

**Trophy reveal (gold tier):**
- Function: `function hmHeroFX(title, sub, emblem)`
- Plays `assets/ui/anvil_reveal.mp4` fullscreen as background
- Trophy emblem, title, and subtitle overlaid on top (z-index 1 relative to the overlay)
- Closes when video ends; fallback closes at 5s
- Award dispatch (where it's called): search `newAwards.forEach` in Block 3

**Chest reveal:**
- Phase 1: `function hmOpenChest()` — plays `assets/ui/chest_reveal.mp4` fullscreen
- Phase 2: `function hmChestReveal()` — triggered by video `ended` event OR "CLAIM REWARD ▸" button; shows +50 XP reward screen with confetti

### 6.14 Service Worker & Caching

**What it does:** Makes the app work offline. Uses a network-first strategy — tries to fetch fresh content, falls back to the cache.

**File:** `sw.js` (in the project root, not inside `assets/`)

**IMPORTANT:** Every time you ship a meaningful code change, you **must** bump the `CACHE_VERSION` string in `sw.js`. If you don't, users on installed PWAs will keep running the old cached version indefinitely.

```js
// sw.js
const CACHE_VERSION = 'hero-mode-v49'; // change this number on every deploy
```

**Convention for the comment:** briefly describe what changed in this version.

**Video files are NOT cached** by the service worker (the `if (url.pathname.includes('/MoveKit_Videos/'))` exemption — add any large video directories here to prevent cache quota exhaustion). The `assets/ui/deck_cards/` images ARE cached.

**Current version:** v51 (as of 2026-08-06)

**Dev gotcha:** if you forget to bump the SW version, existing users won't see your changes. See [Section 9](#9-key-dev-gotchas) for how to force-clear the cache during development.

## 9. Key Dev Gotchas

These are real issues that have cost development time. Read these before debugging.

### Service worker serves stale cache
**Symptom:** you edit `index.html`, reload the browser, but your changes don't appear. New functions are `undefined`. The page looks identical to the version before your edit.

**Cause:** the service worker is intercepting requests and serving cached bytes. This can happen even if the local dev server is running normally.

**Fix:**
1. Open Chrome DevTools → Application → Service Workers → click **Unregister**
2. Go to Application → Cache Storage → delete the `hero-mode-v*` cache
3. Hard reload (Ctrl+Shift+R)
4. OR in the console: `await caches.keys().then(k => k.forEach(n => caches.delete(n))); location.reload()`

**Prevention:** bump `CACHE_VERSION` in `sw.js` on every meaningful commit.

### SW serves cache even when server is dead
If your dev server crashes but the service worker is active, the browser can still serve the app from cache. `preview_start` may report `reused:true`. Edits appear to not apply even though the file is changed.

**Diagnose:** check if the server is actually running (`curl http://localhost:PORT/`). If ECONNREFUSED, the server is dead — restart it.

### CSS animations freeze in headless browser
In the Browser pane (headless), the tab is `visibilityState: hidden`. CSS entrance animations freeze at frame 0 (elements measure wrong heights, opacity stays 0). Screenshots may time out.

**Fix for testing:** run `el.getAnimations().forEach(a => a.finish())` before measuring/screenshotting. This is NOT a bug in the real app — only affects automated browser testing.

### PowerShell heredoc syntax error
PowerShell does not support `<<'EOF'` heredoc syntax. When writing multi-line git commit messages from PowerShell:
```powershell
# WRONG (bash syntax, fails in PowerShell):
git commit -m "$(cat <<'EOF' ... EOF)"

# CORRECT — write message to a temp file first:
git commit -F "C:\path\to\commit_msg.txt"
```

### PowerShell && chaining not available
Use `;` to chain commands (always runs both) or `if ($?) { ... }` for conditional chaining:
```powershell
# WRONG:
git add . && git commit -m "msg"

# CORRECT:
git add .; git commit -m "msg"
```

### `return` statement in javascript_tool
The `javascript_exec` tool evaluates expressions, not statements. Top-level `return` is a syntax error.
```js
// WRONG:
return document.getElementById('foo').innerText;

// CORRECT (just evaluate the expression):
document.getElementById('foo').innerText
```

### `let`/`const` redeclaration across tool calls
Each `javascript_exec` call runs in the same page context. If you used `const av = ...` in a previous call, a new call with `const av = ...` will throw `SyntaxError: Identifier 'av' has already been declared`. Use different variable names in subsequent calls.

### `display:none` vs CSS class `display:flex`
If an element has `class="dc-card"` (which has `display:flex` in CSS) and you add `style="display:none"`, the **inline style wins** in normal CSS (inline has higher specificity). BUT: if the app later calls `element.style.removeProperty('display')`, the CSS class takes over and the element becomes visible again. When hiding elements that have a `display` CSS rule, prefer removing them from the DOM (`el.remove()`) or dynamically creating them when needed rather than toggling visibility.

## 11. Naming Conventions

### localStorage keys
- Prefix: `heromode-` (main data) or `hero-` (identity/gamification)
- Per-profile keys: append `--{profileId}` (e.g. `hero-xp--p1`)
- Per-date keys: append `-{YYYY-MM-DD}` (e.g. `hm-session-note-2026-08-06`)

### Function naming
- `hm*` — hero mode identity/gamification functions (XP, themes, awards, profiles)
- `sl*` — set logging functions (log, PRs, nudges, row refresh)
- `gp*` — goal/plan builder functions
- `ci*` — check-in functions (meals, water, sleep)
- `rb*` — recipe book functions
- `dc*` or `_dc*` — deck of cards functions (`_dc` prefix = private/internal)
- `sh*` — session history functions
- `render*` — renders a section of the UI into a DOM container
- `open*` / `close*` — opens/closes a modal or overlay

### CSS class naming
- `.hm-*` — hero mode specific UI elements
- `.sl-*` — set logging UI (log sheet, set chips)
- `.gp-*` — goal picker / plan builder UI
- `.dc-*` — deck of cards UI
- `.sh-*` — session history UI
- `.sess-sum-*` — session summary overlay
- `.prog-*` — progression guide
- `.auto-spark-*` — sparkline charts
- `.fx-*` — FX overlay elements (emblem, title, rings, particles)

### Service worker versions
Format: `hero-mode-v{N}` where N is a sequential integer. Current: v49. Bump by 1 on every deploy.
